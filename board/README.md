# The board (not in this tree, on purpose)

This folder is a placeholder. There's no code in it, because the board layer isn't part of public Atlas and, as of this writing, the maintainer isn't sure yet whether it ever will be. What follows is what the board is, why it stayed out, and how to bring it back if a future context ever needs the same shape of work-tracking.

## What it is

In the private atlas-v2 repo, the board is a second layer sitting on top of the same entities/observations/reminders core this public tree ships. It lives in its own tables — `board_rows` (the pieces of work themselves: title, status, the Jira-style ticket keys it's tied to, a nickname, sprint info, pin/order state), `workers` (records of spawned sub-sessions tied to a board piece, with the Atlas observation they report progress to), `sprint_slots` (frozen per-sprint slot numbers so "move 6 to 2" stays stable as the board changes shape), `sprint_meta` (a sprint's start/end dates), `plan_entries` and `plan_notes` (Claude's own ordered read of the day and its one-sentence summary of where things stand). `pending_items` also picks up a couple of board-linked fields here — when the board is live, a tray item can promote into a *board row* instead of a bare observation.

On top of those tables sit about twenty MCP tools. `board_add`, `board_list`, `board_get`, and `board_update` cover basic row lifecycle — adding a piece with its required ticket reference, listing the live board oldest-first, fetching one row, editing any subset of its fields. `board_close` is the only sanctioned way a row reaches "done": it writes a ledger event and points the row's `closure_ref` at it, and the database itself refuses `status=done` without that reference, so nothing gets marked closed without leaving a trace. `board_reconcile` is a pure diff against an external ticket snapshot (Jira, or a custom ticket-poller service) — it reports drifted, orphaned, missing, and reassigned pieces without changing anything itself. `board_bump`, `board_unbump`, `board_move`, and `board_order` are the ordering layer: pin a piece to the top, clear a pin, place a piece at a specific slot, or declare a whole intended work order without touching status at all. `board_hold` and `board_release` move a piece to and from an "on hold" band at the bottom of the board. `board_offboard` and `board_restore` take a piece off the live board without pretending it's done — for things like epics or driver tickets whose real work moved somewhere else — and bring it back if that turns out to be wrong. `board_plan_note`, `board_sprint_meta`, and `board_plan_set` feed the Plan tab: a one-sentence read of the day, a sprint's date range, and Claude's own ordered take on how the sprint gets finished. `worker_add`, `worker_list`, and `worker_update` register a spawned worker thread as a structured row instead of free text buried in a chat — its name, task, tied ticket(s), the board piece it's scoped to, and the Atlas observation it writes status updates to.

There's also a live web view. Private `src/server.js` runs a second, separate Express app on its own port (`BOARD_PORT`, 7795 by default) with three routes: `/` renders the whole board as one read-only HTML page — the live pieces grouped by sprint, the pending tray, the research shelf, reminders, and workers, refreshing itself every 30 seconds; `/health` is a liveness check; `/api` is a JSON feed of the same state, meant to be curled by something like a session-start hook so the board can be injected into a fresh conversation deterministically instead of relying on a tool call. It's LAN-only with no auth of its own — it assumes the network it's running on is already trusted.

## What it does

The shape is sprint-based work tracking: tickets or pieces of work move through todo, in_progress, on_hold, and done, with the database enforcing the two rules that matter — a row never gets hard-deleted (offboarding hides it, closing retires it, but the row and its history stay forever), and a row can't reach "done" without a ledger reference explaining why. Ahead of the board sits a pending tray for things that showed up without a ticket yet, which get merged into an existing piece, promoted into a new one, or dismissed — always with the reasoning kept, never silently dropped. Alongside the board, worker records let the maintainer track a spawned sub-session ("worker 6, do X") against the piece it's working on, so "what's my worker doing" is a query against a table instead of scrollback to go dig through.

## Why it's not in public core

This split was a deliberate decision, not an oversight — see commit `5fce25a`, "Public release tree: best-of Atlas without the board," which drew this exact line the day the public tree was first cut. The general memory core — entities, observations, reminders, the tray, the shelf — starts blank and assumes nothing about what kind of work you do with it, which is what makes it something anyone can point Claude at. The board is the opposite of that: it's built around sprints, tickets, and a Jira-shaped notion of "in progress" versus "done" that reflects one particular job, not a general-purpose shape. Baking that into the general-purpose tool would mean forcing everyone else's Atlas to think in sprints whether or not that's how they work. So the board stays private, but the code isn't going anywhere and isn't hard to bring back — this file exists so that decision, and the path back from it, doesn't have to be rediscovered from scratch later.

## How to add it back

If a future context turns out to need the same shape of work-tracking, the honest expectation is a few real hours of porting, not a five-minute copy-paste — and whoever does it should diff against whatever this public tree has drifted to by then, not assume the schema and tool set described above are still exactly current.

Start with the tables. In the private repo, `grep -n "CREATE TABLE IF NOT EXISTS board_rows" src/db.js` (and the same pattern for `workers`, `sprint_slots`, `sprint_meta`, `plan_entries`, and `plan_notes`) will find each one's current definition — line numbers aren't given here on purpose, since they'll have moved by the time this is read. Copy those `CREATE TABLE` blocks into this public tree's `src/db.js` as one new additive migration, following the same `PRAGMA user_version` ladder this file already uses (see the v4/v5 migrations added alongside the core memory tier for the pattern). Watch for the couple of `pending_items` columns that are board-specific (the ones that let a tray item promote into a board row instead of a bare observation) — those need to come along too if the tray is meant to feed the board the same way it does privately.

Then the tools. `grep -n "guarded('board_" src/tools.js` and `grep -n "guarded('worker_" src/tools.js` in the private repo will list all twenty definitions with their current line numbers. Each one is a self-contained `guarded(name, {title, description, inputSchema}, handler)` block plus one or two functions in `db.js` — copy them across in the same shape, and expect to touch the wording here and there since the private descriptions sometimes reference maintainer-specific context (Jira, an internal ticket-poller, particular naming conventions) that would need to be genericized for a public-facing tool description.

If the live web view is wanted too and not just the MCP tools, the board routes in private `src/server.js` (`grep -n "BOARD_PORT\|boardApp\." src/server.js` will find the second Express app and its three routes) are a separate, self-contained piece — they read straight from the same tables, so they can be ported once the schema and tools above are in place, as a second pass rather than part of the same change.

Whichever pieces get ported, they need their own tests (following this tree's existing pattern of starting every test from an empty database) and a README/CHANGELOG entry describing what shipped, the same as any other change here.
